# Architecture

One process per replica, passing each client's [native API](glossary.md) through to a provider that serves it: the Anthropic Messages API for Claude Code and Anthropic SDK clients, and the OpenAI Responses and Chat Completions APIs for Codex and OpenAI SDK clients. Wye never translates between provider APIs ([product.md](product.md#non-goals)).

## System view

```text
                         Git repository
                           wye.toml
                              │
                   CI checks + GitOps rollout
                              │
            deploy same config version to replicas
                              │
App / Claude Code / Codex ──> ingress / Kubernetes Service
                              │
                    ┌─────────┴─────────┐
                    ▼                   ▼
              Wye replica A       Wye replica B
                    │                   │
            authenticate        authenticate
            request policy      request policy
            route / proxy       route / proxy
            stream / cancel     stream / cancel
                    └─────────┬─────────┘
                              ▼
                        LLM providers

              Each Wye replica ──OTLP──> OpenTelemetry backend
```

Replicas never communicate at request time. A new request may land on any ready replica. A stream stays on its replica until completion; active streams are not migrated.

Infrastructure provides service discovery, TLS/ingress, scheduling, replica count, rollout, secret delivery, and any aggregate rate limiting. Wye provides its listener, graceful shutdown, and health endpoints ([operations.md](operations.md)).

## Request path (target)

1. Validate endpoint, framing, and request size.
2. Verify the signed [gateway token](glossary.md) against a configured verification key.
3. Enforce static model permissions and per-request limits ([policy.md](policy.md)).
4. Resolve a model alias; select the route that serves this endpoint natively, and among its [upstreams](glossary.md) the one policy picks (`cache_affine` or `ordered`).
5. Apply allowlisted rewrites (the [served model](glossary.md), the provider's model id, agent-aware model routing).
6. Forward upstream unchanged beyond the allowlist.
7. Stream incrementally with downstream backpressure; preserve tool calls and event semantics.
8. Propagate cancellation, apply [failover](glossary.md), release request resources.
9. Extract reported usage, or mark it unknown; export telemetry asynchronously.

Implemented for all three APIs: steps 1, 2, 3 (model permissions and output-token ceilings), 4 (aliases, the route per endpoint, the upstream among a route's), 5 for aliases and the provider's model id (Bedrock), 6-8, and 9 as usage records in a JSON-lines log and as OTLP logs, metrics, and spans. Step 8 includes failover before output on routes that configure it. Not built: cost ceilings in step 3, agent-aware routing in step 5.

## Runtime stack

| Concern | Technology |
|---|---|
| Async execution | Tokio |
| HTTP | Hyper 1.x, `hyper-util`, `http-body-util` |
| TLS | Rustls (`ring` provider) upstream, built-in web PKI roots plus `upstream.ca_file`; deployment terminates inbound TLS |
| Tokens | `ring` Ed25519, ECDSA P-256, and RSA verification, `base64` |
| Hashing | `xxhash-rust` xxh3 (prompt hashes), `ring` HMAC-SHA256 (their exported tags) and SHA-256 (session trace ids) |
| Config / JSON | Serde, `toml`, `serde_json`; hand-written streaming scanners for request bodies and SSE (`memchr`) |
| Buffers | `bytes` and streaming bodies |
| Instrumentation | Usage records as a JSON-lines log on stdout and as OTLP logs, metrics, and spans |
| Edge | Separate WASM adapter later |

The OTLP exporter is hand-written (OTLP/HTTP JSON on the existing hyper client), instead of the OpenTelemetry Rust SDK and its gRPC stack.

Direct Hyper gives explicit control over request and response bodies. Reconsider Axum if endpoints and middleware grow enough to justify it.

Immutable configuration, connection pools, and in-flight request state are compatible with statelessness; persistent conversations, global quotas, and cumulative spend accounting are not.

## Public API

Implemented:

- `POST /v1/messages`, `POST /v1/messages/count_tokens`: Anthropic Messages, native passthrough for Claude Code and Anthropic SDK clients, when `[upstream]` or `[routes.claude]` is set.
- `POST /v1/responses`: OpenAI Responses, native passthrough for Codex and OpenAI SDK clients, when `[routes.openai]` is set ([Codex integration](#codex-integration)), with usage and cost in records ([usage extraction](#usage-extraction)).
- `POST /v1/chat/completions`: OpenAI Chat Completions, native passthrough for OpenAI SDK clients and OpenAI-compatible agents, on the same `[routes.openai]`.
- `GET /healthz`, `GET /readyz`: operational probes; `HEAD /api/hello`: Claude Code's warm-up probe.
- `GET /v1/models`: with `[discovery]`, the configured catalog narrowed to the models the caller may use (`[auth] models`, then the token's `models` claim), so Claude Code's model picker shows only permitted models. Authenticated when `[auth]` is set; one page (`has_more: false`); no upstream contact and no usage record. Claude Code queries it only with `CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY=1`, with a 3-second timeout, and keeps ids containing `claude` or `anthropic`. Codex's catalog request (`GET /v1/models?client_version=...`, its own format) gets `404`, so Codex uses its bundled catalog.

Every other path gets `404 not_found_error`; so does an API whose route is not configured, with a message naming the config section that would serve it.

An `ANTHROPIC_BASE_URL` or `OPENAI_BASE_URL` override works only when the client respects it and uses an implemented endpoint. Base-URL compatibility is not compatibility with proprietary SDK extensions.

### Claude Code gateway contract

Claude Code documents what a gateway must do ([gateway compatibility guide](https://code.claude.com/docs/en/llm-gateway-protocol)). Acceptance tests encode it:

- Match on path, not full URL: inference posts to `/v1/messages?beta=true`; forward the query string.
- Forward all `anthropic-*` request headers and all body fields unchanged, as open lists. Never allowlist `anthropic-beta` values: capabilities pair a beta header with a body field, and stripping one half produces `400`s on the next Claude Code release.
- Forward `retry-after`, `x-should-retry`, and `anthropic-ratelimit-unified-*` response headers, and upstream error bodies unmodified; Claude Code's retry and capability-recovery logic matches upstream error wording.
- Relay every SSE event, including `ping`. Claude Code aborts an idle stream and treats a stream that ends before `message_delta`/`message_stop` as dropped.
- Forward the `system` array unchanged; its first block is an attribution block the Anthropic API strips by position.
- Consume, never require, `x-claude-code-session-id`, `x-claude-code-agent-id`, `x-claude-code-parent-agent-id`, and the gateway hint headers (`x-claude-code-request-class`, `-agent-type`, `-compaction`, `-context-compacted`, `-prompt-id`, `-prev-tool-durations`) for telemetry attribution, [agent-native visibility](research.md#agent-native-directions), and, later, [agent-aware routing](research.md#1-agent-aware-routing). A custom base URL receives hint headers only when developers set `CLAUDE_CODE_GATEWAY_HINT_HEADERS=1`, as `wye claude` does. Values are client-supplied: bound and validate them before they become telemetry attributes, and never let them authorize anything.
- Answer the best-effort `HEAD /api/hello` warm-up probe with an empty `200` before authentication; it carries no data and reaches no upstream.
- `/v1/messages/count_tokens` is unbilled: it requires authentication and model permission but skips the output-token ceiling (and, once built, cost admission).
- Gateway-generated errors use Anthropic's error JSON shape and status codes, so Claude Code's retry and recovery logic reads them as it reads upstream errors. Wye's own `529 overloaded_error` (concurrency or held-bytes limit, always before any upstream contact) carries `retry-after: 1` and `x-should-retry: true`: integer seconds at most 60, or Claude Code stops retrying.
- Gateway sessions are not eligible for Claude Code's HIPAA configuration; regulated teams must know before adopting Wye.
- Claude Code sends background requests to a second, smaller model unless one is pinned; model permissions must cover it or those requests fail.
- Interactive and background sessions open with a one-token probe (`max_tokens: 1`, no tools, not streamed). With a claude.ai login behind a custom base URL, Anthropic answers it `429 rate_limit_error`, with or without Wye in the path (checked 2026-10-30), and Claude Code carries on, so one 429 per session start in the usage log is expected.

The guide changes with the client. Re-run the contract tests against each targeted Claude Code release.

### Codex integration

What Codex sends a custom provider, from its source (openai/codex at `970111f`, read 2026-10-26) and its gateway guide (learn.chatgpt.com, "Gateway compatibility"):

- A custom `[model_providers.<id>]` with `wire_api = "responses"` gets `POST {base_url}/responses` over HTTP with SSE; its `supports_websockets` defaults to false, so no WebSocket transport. The built-in `openai` provider (also reached through `openai_base_url`) tries WebSockets first and falls back to HTTP; `wye codex` therefore defines its own provider.
- The bearer token comes from the environment variable the provider's `env_key` names, as `Authorization: Bearer`: with `[auth]` a gateway token, which Wye verifies and replaces with the OpenAI key. Request bodies are zstd-compressed only with a ChatGPT login on the built-in provider, never for an API-key custom provider, so Wye reads plain JSON. Codex serializes `model` first ("gateways may inspect request bodies incrementally"), so [the hold](glossary.md) usually reads one chunk.
- Headers for attribution, mapped onto the fields Claude Code's headers fill (implemented):
  - `session-id` → `session_id` (and cache affinity, and the session trace).
  - `thread-id` → `agent_id` and `x-codex-parent-thread-id` → `parent_agent_id` (a thread is one agent's conversation).
  - `x-openai-subagent` → `agent_type`, and [`request_class`](glossary.md) (`collab_spawn` → `subagent`, `compact` → `compaction`, `review` and `memory_consolidation` → `auxiliary`, unknown → `other`). Codex omits the header only on the main thread, so a request without it is `main` when its `originator` names Codex (`codex_cli_rs`, ...), and unclassified from other clients.
  - `x-codex-turn-metadata` (JSON, with the request kind) is not read: the request path reads only headers.
- Over HTTP Codex replays the whole input each turn and sends no `previous_response_id` (that is WebSocket-only), so no upstream-held state pins a request yet.
- Retries: `request_max_retries` (default 4) on 5xx and transport errors, never on `429`; `stream_max_retries` (5) for interrupted streams. Wye's overload answer on Responses is therefore `503` with `retry-after`, which Codex and the OpenAI SDKs retry.

Gateway-generated errors on `/v1/responses` use OpenAI's shape: `{"error": {"message", "type", "param", "code"}}`, with `type` `invalid_request_error` or `server_error` and `code` naming Wye's reason (`permission_error`, `authentication_error`, `overloaded_error`, ...).

## Forwarding contract

Each endpoint forwards to the corresponding upstream endpoint without converting between APIs.

**Bodies.** Preserve request JSON, unknown fields, tool definitions, and provider-native options. The request body streams upstream unchanged beyond the allowlist below and is never re-serialized.

`server.max_request_body_bytes` (default 32 MiB, Anthropic's limit) counts the bytes the client sent: a declared length past it gets `413` at once, and a body without one gets `413` when it passes the limit mid-upload. With [model permissions or output-token ceilings](policy.md#gateway-tokens), aliases, or a provider with its own model ids, only the start of the body is held, until its top-level `model` has been read, within `server.max_held_request_bytes`.

Never buffer the generated response. Relay SSE bytes without parsing or rebuilding events; HTTP chunks are not SSE event boundaries. Preserve non-streaming JSON and upstream error bodies.

**Request rewrites.** Wye rewrites only an explicit allowlist of request fields; everything else passes through byte for byte, and a rewrite splices the new value in place. Each field, when it is rewritten, and why:

- **`model`**, for a [model alias](#model-aliases-and-upgrade-checks) (implemented), a Claude provider's model id (Bedrock, implemented), or size-aware routing (planned, [roadmap](roadmap.md#m2c-fewer-expensive-tokens)): replace an alias with the model config maps it to, a model policy selects for the request class, or the selected provider's id for the same model (`anthropic.claude-opus-5-5` on Bedrock). Never a different model family.
- **`model` → URL, `anthropic_version`**, for Vertex AI (planned): Vertex names the model in the URL and needs `"anthropic_version": "vertex-2023-10-16"` in the body: the top-level `model` member is cut and the version member spliced in; every other byte is unchanged.
- **`max_tokens` / `max_completion_tokens` / `max_output_tokens`**, in hard cost mode (planned): insert the output bound used in the [cost ceiling](policy.md#provable-cost-ceiling) when absent; lower a caller value only when the route explicitly accepts truncation, otherwise refuse; never raise a caller value. On Messages, never lower below `thinking.budget_tokens`; refuse instead.
- **`stream_options.include_usage`**, for streaming Chat Completions with usage accounting (planned, off: see [open decisions](#open-design-decisions)): OpenAI omits streamed usage otherwise ([usage extraction](#usage-extraction)); until the default is decided, clients that want usage set it themselves.

Each rewrite is set in config (aliases for every route, model ids by the upstream's provider), covered by tests, and reported by `wye explain`. Adding a field to this list is a design change.

### Usage extraction

A bounded, read-only observer reads the same bytes Wye relays. It never delays, buffers, or changes them, and an oversized or malformed event marks usage `unknown` instead of failing the stream. `UsageScanner` picks the scanner per API as an enum; each scanner's limits are documented on its constants and under [Fixed limits](#fixed-limits).

A body wrapper emits one record when the body is dropped, so every outcome is recorded. A request the client leaves before its response headers is recorded as cancelled with nginx's status `499`. A body also counts as completed once its declared length is delivered: the client connection stops polling then, and an HTTP/2 upstream may send its end-of-stream frame after the data.

- **Messages streams** always carry usage (`message_start`, `message_delta`), so no rewrite is needed. Tool names come from `content_block_start`.
- **Responses streams** carry usage only in the terminal event, whose data line holds the whole response, often megabytes. It is lexed with constant memory, so a lookalike `"usage"` in generated text is never read. `response.output_item.added` gives tool calls by name, and hosted tools billed per call mark the cost partial. A stream cut before the terminal event is `unknown`; there is no `partial`, because OpenAI sends no interim counts.
- **Chat Completions streams** carry usage only in a final chunk the client asks for with `stream_options.include_usage`. Wye does not add the field (the [rewrite](#forwarding-contract) is an open decision: the extra chunk with empty `choices` trips some clients), so a stream without it records `unknown`. `prompt_tokens` include cached tokens and are split like Responses' `input_tokens`.
- **Non-streaming JSON** (all three APIs) carries `model` and `usage` as top-level members after the generated content. A constant-memory lexer keeps those and counts tool calls among `content` blocks or `output` items; Chat's sit in `choices` and are not counted. A body cut off before `usage` is `unknown`.
- Error responses, `count_tokens` (which generates nothing), and responses that are neither SSE nor JSON are `not_observed`.

**Headers and destination.** Strip hop-by-hop headers, including those named by `Connection`. Replace caller authorization (`Authorization` or `x-api-key`) with the configured [provider key](glossary.md), except in explicit loopback [caller-credential passthrough](policy.md#caller-credential-passthrough); with the provider key, also drop the caller's `OpenAI-Organization` and `OpenAI-Project`, which would choose what the provider key bills. Forward only appropriate end-to-end headers.

Replace `accept-encoding` with `identity`: Claude Code asks for Brotli and Anthropic complies, which would hide usage from the [observer](#usage-extraction); an uncompressed response adds only bytes, decompressing a copy adds CPU overhead per event ([benchmarks.md](benchmarks.md#current-harness-and-baseline)).

The caller never selects the upstream destination (no open proxy or SSRF surface). Preserve the configured base-path prefix.

**Backpressure and cancellation.** Downstream body polling applies backpressure. No unbounded queues or detached readers. Client disconnect releases or cancels upstream work, verified by integration tests. Already generated tokens may still be billed.

**Errors.** Before downstream headers are sent, local failures produce a gateway error in the client-facing API's error shape. Upstream error bodies pass through unmodified. A refusal the request body raises after forwarding began (a late output-token field, a repeated `model`, the size limit) aborts the upstream request and gets its own status, from an HTTP/1.1 or HTTP/2 upstream alike (`upstream/refusal.rs`). After headers are sent, an upstream failure terminates the stream; it cannot become a new JSON error response.

**Timeouts.** Four on the upstream and client sides, two on a held body, and no total request timeout, which would kill valid generations:

- Connect: short, over the TCP connect and the TLS handshake together. A peer that stalls the handshake fails as a refused connection, so failover applies.
- Response headers: several minutes, because a non-streaming generation sends no headers until it completes (Claude Code falls back to non-streaming requests after a stream failure).
- Streaming inactivity: longer than the provider's `ping` interval.
- Client write: a connection whose response writes make no progress for `client_write_timeout_secs` is closed, cancelling its upstream request, because a client that stops reading leaves its response unpolled and the inactivity timer never runs.
- Held body: while Wye reads `model`, 60 s without a byte or 5 minutes in all gets `408` (`HOLD_IDLE_TIMEOUT`, `HOLD_TIMEOUT`).

Shutdown: [operations.md](operations.md#health-and-shutdown).

## Failover

Wye does not retry an ambiguous failure or fail over after output: an ambiguous failure may already have incurred charges, and switching providers after output starts cannot preserve the response. It does not retry the same provider either: clients retry on their own, guided by the `x-should-retry` and `retry-after` headers Wye forwards, and gateway retries would multiply attempts and risk duplicate billing.

The one exception is [failover](#claude-across-providers-and-upstreams) to a route's next upstream, on `[routes.claude]` and `[routes.openai]` alike, after a [rejection](glossary.md) that proves the request was not processed (`429`, `529`, a connection refused or cut before the body was delivered whole), before any response byte was sent. Do not claim exactly-once execution.

## Providers

Anthropic, Claude Platform on AWS, and Bedrock serve the Messages API, and OpenAI serves `/v1/responses` and `/v1/chat/completions`; Vertex is planned (M4).

A closed `Provider` enum (`config::Provider`) selects how Wye authenticates (`x-api-key` or `Authorization: Bearer`), any header the provider requires (Claude Platform on AWS's workspace), and its model-id prefix (Bedrock's `anthropic.`). A closed `Api` enum (`gateway-core/src/api.rs`) holds what differs per native API: the output-token field, the session header, the error shape. There is no trait with one implementation and no translation layer.

A request for an endpoint no configured provider serves is refused, never converted. Passing provider-native options through does not mean Wye interprets or enforces them.

### Upstream connections

hyper-util's client pool keeps a single HTTP/2 connection per host and never opens another, so requests beyond the provider's concurrent-stream limit would queue inside it. `upstream/pool.rs` keeps 64 lanes, each a client with its own connection, connected lazily. Each request takes a slot on the least loaded lane, held by the response body until the stream ends: sequential traffic reuses one connection, `k` concurrent requests use up to `k`, and beyond 64 the load stays even. Spreading is deliberate: `h2` guards all streams of one connection with one mutex, and packing streams onto a connection made that lock the dominant overhead of the TLS path.

Streams on a lane share its HTTP/2 connection window. With hyper's default (5 MiB, 2 MiB per stream), three clients that stopped reading filled it and stalled every other stream on the lane. So the connection window is the protocol maximum, and buffering is bounded per stream instead (256 KiB window, measured 0.56 MB of heap): a stalled client holds only its own stream, and only until `client_write_timeout_secs`.

On the client side, each connection's kernel send buffer is fixed at 128 KiB (`server.rs`; Linux doubles the value, so 256 KiB there) instead of autotuning to as much as 4 MiB. The worst case, every in-flight request stalled at once, is `max_concurrent_requests` × about 0.7 MB.

### Upstream-held state

Some requests reference state stored by a specific provider account: Responses `previous_response_id` (with `store=true`), stored conversations, uploaded file IDs, and provider cache entries. Wye stores none of it, but [upstream selection](glossary.md) must respect it:

- A request that references upstream-held state is pinned to the upstream that can resolve it, or refused with an explicit error. It is never sent to another upstream.
- Determining that upstream must be stateless: from the route configuration (a route with a single eligible upstream) or the gateway token. If neither identifies it, refuse.

A route with one upstream resolves every stored response. With several OpenAI upstreams, [`cache_affine`](#cache-affinity) already sends every request of a session (or, without a session id, of a token subject) to the same upstream, so a `previous_response_id` reaches the upstream that stored the response as long as the route's upstreams and weights do not change; after a change, a moved session's next reference fails with OpenAI's own `404`, not a misrouted success. Response ids do not name their upstream, so Wye cannot refuse such a request itself. Codex over HTTP sends no `previous_response_id` (it replays the input; [Codex integration](#codex-integration)).

### Cache affinity

Provider prompt caches are per account (and sometimes per region), and cached input is priced at a large discount. Cost routing that spreads one conversation across accounts or providers forfeits that discount.

When a route has several upstreams, Wye chooses by weighted rendezvous hashing (`gateway-core/src/route.rs`), keyed by the client's session id (Claude Code's or Codex's), otherwise the token subject, otherwise nothing (without `[auth]` Wye serves one loopback user, so every such request picks the same upstream).

Each upstream scores `weight / -ln(u)`, with `u` from an xxh3 hash of the key seeded by the upstream's id; the highest score wins, so a key lands on an upstream with probability proportional to its weight. The same session reaches the same upstream from any replica, with no shared state. It moves only when its upstream leaves the route or the weights change; adding an upstream moves only the keys it now wins, and reordering the config moves nothing. A test pins the choice for fixed keys, since a change of hash or scoring would move every session during a rolling update.

Hashing a stable request prefix for SDK callers without a session id is not implemented: it would need the body before choosing. The cost benefit is a hypothesis to measure ([research.md](research.md#questions-to-test)).

Pure [cache affinity](glossary.md) can overload one upstream when a few keys dominate traffic, a capacity loss recent serving research reports ([related work](research.md#related-work)). The load bound must stay stateless. Implemented: a static share per upstream in config (`weight`), which spreads sessions, not tokens, so one heavy session still stays on one upstream. Open: a placement plan fitted offline from telemetry and committed to config. Every replica still computes the same choice.

### Model aliases and upgrade checks

#### Aliases

A client asks for a stable name and config decides the model:

```toml
[[aliases]]
name = "coding-default"
model = "claude-opus-5-5"
# Staged rollout: tokens whose subject matches get another model first.
when = [{ subjects = ["team-canary-*"], model = "claude-sonnet-5-5" }]
```

- Resolution reads the top-level `model` with the existing [policy scanner](policy.md#gateway-tokens) hold (Claude Code and the SDKs send `model` first; configuring `[[aliases]]` makes the hold apply to every request) and splices the served model's name in place of the alias: the held chunks are sliced around the value, so only the new name is allocated, every other byte is unchanged, and `content-length` is adjusted by the difference. Names that are not aliases pass through untouched, so aliases are opt-in per request.
- Rollout: `when` rules match the token's subject (exact or a prefix ending in `*`, as in model permissions); the first match wins, and callers without a token get the alias's `model`. Resolution is one step: an alias names a model, never another alias.
- Policy applies to the model that runs: model permissions apply to the served model, and pricing to the model the provider reports, which is the served one. `GET /v1/models` lists aliases after the catalog's models, each when the model it resolves to for that caller is permitted. Claude Code's model picker keeps only ids containing `claude` or `anthropic`, so aliases meant for it are named accordingly (`claude-coding`).
- Visibility: `requested_model` in records ([operations.md](operations.md#telemetry)); `wye explain` prints the resolution, and a policy test can pin the served model, so a rollout is reviewed like any policy change.
- Overhead, with every benchmark request aliased: one allocation per request for the hold, one more when the name's length changes, CPU per request within noise. With aliases alone the rest of the body is not lexed (Claude Code-shaped uploads 1.64 vs 1.49 ms per MB, within noise; with the repeated-`model` check, 2.16).
- An alias names one model. Mapping one name to several providers of that model is [a route](#claude-across-providers-and-upstreams), not a second alias mechanism.

#### Upgrade checks

Moving an alias, or a client, to a new model fails in production when the new model rejects what the old one accepted. Wye ships a rule table of each model's breaking request changes, every rule citing the provider's migration notes and covered by its own test (`gateway-core/src/upgrade.rs`):

Each rule, the request field it reads, and the models that reject it (dated ids included):

- **`thinking_disabled`** (`thinking.type` `disabled`): Opus 5.5; Sonnet 5.5; Fable 5, 5.1; Mythos 5.1 (Opus 5 and Haiku 5.5 only at effort `xhigh` or `max`, not reported).
- **`budget_tokens`** (`thinking.type` `enabled`, a manual budget): Opus 4.7, 4.8, 5, 5.5; Sonnet 5, 5.5; Haiku 5.5; Fable 5, 5.1; Mythos 5.1.
- **`forced_tool_choice`** (`tool_choice.type` `any` or `tool`): Opus 5.5; Sonnet 5.5; Fable 5.1; Mythos 5.1.
- **`computer_tool`** (`tools[].type` `computer_20250124` or `computer_20251124`): Opus 5.5, Sonnet 5.5, Haiku 5.5 on the Claude API and Google Cloud (Bedrock still takes `computer_20251124` on Opus and Sonnet 5.5).
- **`prefill`** (the last `messages[]` entry is an assistant turn): Opus 4.6 and later; Sonnet 4.6, 5, 5.5; Haiku 5.5; Fable 5, 5.1; Mythos 5.1.
- **`sampling`** (`temperature`, `top_p`, or `top_k`): Opus 4.7 and later (any value); Sonnet 5, 5.5, Haiku 5.5, Fable 5, 5.1, Mythos 5.1 (non-default values; reported for any, since the guide says to omit them).
- **`system_role`** (a `messages[]` entry with role `system`): Opus 4.6, 4.7; Sonnet 4.6, 5 (mid-conversation system messages start with Opus 4.8).

Source: Anthropic's model migration guide, its per-model sections (the [Opus 5.5 guide](https://platform.claude.com/docs/en/models/opus-5-5/migration-guide) read 2026-10-26, the models per rule re-read 2026-10-30). Only rejections the body shows are rules: the effort level, the platform, and a parameter left at its default can make a listed model accept the request. The deprecated `output_format` is rejected without a beta header on every model, so it is not an upgrade rule.

```toml
[upgrade_check]
targets = ["claude-opus-5-5"]          # models an alias or a client may move to; up to 16
# share of sessions (or, without one, clients) checked; default 100
sample_percent = 10
```

- Scan: for sampled requests, a constant-memory structure scanner on the forwarded body reads only the fields the rules name (keys at the first three levels; `thinking.type`, `tool_choice.type`, `tools[].type`, `messages[].role`) and records which rules each target breaks. Sampling is by Claude Code session id, or by the token's subject for SDK callers without one, alike on every replica.
- Overhead: on a Claude Code-shaped 1 MiB body it scans in 0.77× the time of the model-permission scan and half that of cache diagnostics (same machine, same body), so about 0.5 ms per MB in the gateway.
- Records: `upgrade_issues` in the usage record (`{"claude-opus-5-5": ["budget_tokens", "prefill"]}`; `{}` for a checked request no target rejects) and the `wye.upgrade.issues` metric, so the [OpenTelemetry backend](glossary.md) shows which clients would fail before the switch.
- Offline: `wye explain --config wye.toml --target-model claude-opus-5-5 request.json` (repeatable; without it, the configured targets) prints each issue with the fix and its source; `wye report` lists issues by target, rule, and client.
- Report only: the request is forwarded unchanged ([non-goal](product.md#non-goals)). The rule table is versioned with Wye.

### Claude across providers and upstreams

Status: several upstreams, `cache_affine` and `ordered` selection, failover before output, and Claude Platform on AWS and Bedrock with API keys are implemented; Vertex, SigV4, and excluding an upstream by model or feature are planned.

The same Claude models are sold by four providers. Wye can serve one Claude Code fleet from several of them, choosing per request and failing over, because all four speak the Anthropic Messages API with small, known differences. Wye only chooses among them: no request is translated or sent to another model family.

Each provider's endpoint, request, stream, auth, and model id:

- **Anthropic**: `api.anthropic.com/v1/messages`. Messages over SSE. Auth: `x-api-key`. Model id: `claude-opus-5-5`.
- **Claude Platform on AWS** (Anthropic-operated): `aws-external-anthropic.{region}.api.aws/v1/messages`. Messages, same-day parity, over SSE. Auth: SigV4 (`aws-external-anthropic`) or short-term API key; workspace id required. Model id: `claude-opus-5-5`.
- **Amazon Bedrock**, Messages endpoint (Opus 4.7 and later): `bedrock-mantle.{region}.api.aws/anthropic/v1/messages`. Messages over SSE. Auth: SigV4 (`bedrock-mantle`) or a Bedrock API key in `x-api-key`. Model id: `anthropic.claude-opus-5-5`.
- **Google Vertex AI**: `aiplatform.googleapis.com/v1/projects/{p}/locations/{loc}/publishers/anthropic/models/{model}:streamRawPredict`. Messages without `model`, with `anthropic_version`; SSE (to verify). Auth: OAuth access token (`Authorization: Bearer`). Model id: `claude-opus-5-5`.

Sources: Anthropic's platform pages for Bedrock, Vertex, and Claude Platform on AWS (read 2026-10-22). The legacy Bedrock `InvokeModel` path streams AWS event-stream frames, not SSE, so it would need re-framing per event and is excluded. Partner platforms lack some first-party features (Files API, URL sources, some server tools, `fallbacks`); a request that uses one fails at that provider with the provider's own error, and Wye does not hide the difference.

**Selection** (implemented; OpenAI upstreams too). Upstreams are configured per route (`[[routes.claude.upstreams]]`, all serving the same models). Wye picks deterministically, from any replica alike: [`cache_affine`](#cache-affinity) by session id (prompt caches are per provider and account, so a session stays on one), weighted by configured shares; or `ordered`, the first upstream in config, the rest only on failover. Not built: excluding an upstream by the request's model or a feature it is known not to support. No health state is shared or remembered between requests. Each upstream keeps its own connection lanes and provider key; `forward_caller_credential` stays a single-`[upstream]` mode.

**Failover within a request** (implemented, on `[routes.openai]` too) happens only where it cannot duplicate billing, and only before any response byte reached the client. A `429`, a `529`, a refused connection, or a connection lost before the request body was delivered whole moves the request to the next upstream in its ranking: the next-highest rendezvous score, or config order with `select = "ordered"`, so every replica fails a session over to the same second upstream. An incomplete request cannot have been processed, which covers a provider that rejects early and closes during the upload. A `5xx` after the provider may have accepted the request gets no failover ([retries](#failover)), and config refuses any other reason.

Resending needs the body, which hyper consumes. `wye/src/failover.rs` keeps each chunk it sends (shared `Bytes`, not copies), up to `failover_max_body_bytes` per request (default 8 MiB) and `failover_max_kept_bytes` across the process (default 256 MiB, separate from `server.max_held_request_bytes`, so kept bodies never starve the hold that reads `model`).

A dropped attempt hands back its sent chunks plus the unread rest of the client's body through a oneshot channel, so a rejection that arrives mid-upload moves on too: the next upstream gets the sent bytes, then the rest as the client sends it. A body over either bound, or an attempt still holding its body 100 ms after the rejection (hyper still writing), is answered as it is, never refused and never partly resent.

Records carry `failovers` (`[{"upstream":"a","status":429}]`), OTLP logs `wye.failovers`, and the `wye.failovers` metric counts rejections by upstream and reason. Claude Code retries on its own, so failover improves latency and availability but is not needed for correctness. A failover costs that turn its prompt-cache discount at the new provider; cache affinity brings the next turn back.

**Claude Platform on AWS** (implemented, API keys only): `provider = "claude-platform-aws"` with `base_url = "https://aws-external-anthropic.{region}.api.aws"` and the required `workspace_id`; Wye sends the key as `Authorization: Bearer` and `anthropic-workspace-id` on every request. Requests, responses, and model ids are the first-party API's, so nothing else changes (platform.claude.com, "Claude Platform on AWS", read 2026-10-26). Its short-term API keys last at most 12 hours and Wye reads keys at startup, so a deployment on them restarts (or rolls) within that window until a key refresher lands; SigV4 (service `aws-external-anthropic`) is the open decision below.

**Amazon Bedrock** (implemented with API keys, not yet checked against the live service): `provider = "bedrock"` with `base_url = "https://bedrock-mantle.{region}.api.aws/anthropic"`.

- Wye sends the Bedrock API key as `x-api-key`, as Anthropic's page says for the standard SDK. AWS's page shows `Authorization: Bearer`, and [one live request](research.md#verification-needed) will settle it.
- Model ids carry an `anthropic.` prefix. On a route with a Bedrock upstream, Wye holds each request until its `model` and gives each attempt its upstream's id: `claude-opus-5-5` becomes `anthropic.claude-opus-5-5` for Bedrock and stays as sent for the others, with `content-length` adjusted. Routes without a Bedrock upstream are unchanged.
- Records, OTLP, and pricing see the model the provider reports. Whether Bedrock reports its `anthropic.` id there, which a price entry would then need to name, is part of the live check.
- A failover resend gets the next upstream's id, in the bytes already sent or in the unread rest; a value split between the two (a rejection in the middle of the first chunk) is answered as it is.

**Auth without state** (planned for SigV4 and Vertex): see [open decisions](#open-design-decisions).

**Telemetry and cost** (implemented). Records, OTLP, and `wye report` split by the upstream's `id`, which names the account; config maps it to its provider. Partner and regional prices differ, so price table entries can be scoped to upstreams ([policy.md](policy.md#price-table)).

## Configuration

One TOML file, loaded at startup, is the source of truth for routes and their providers, token verification, limits, aliases, and prices. Secrets are referenced by environment variable or file, never stored in Git, images, or IaC state.

The runtime resolves them; the core validates configuration without resolving secrets. Refuse unknown fields, invalid URLs or limits, broken references, duplicate IDs, unsupported provider/API pairs, missing credentials, and a policy that needs prices without them at startup. Never print secrets or log request bodies by default.

No hot reload; changes require a restart (or rolling deploy). A config snapshot stays consistent within a request. Planned: include the config version in logs and traces to diagnose rollout skew.

### Schema

[`examples/wye.toml`](../examples/wye.toml) is the reference: every field with its default, its limits, and what it does, kept valid by a test that parses it with every section enabled. Only `listen`, `base_url`, and one credential are required. `[upstream]` is the short form of a `[routes.claude]` with one upstream, and the only form that can forward the caller's credential; `[routes.openai]` adds OpenAI, and at least one route is required.

Config defaults are the `DEFAULT_*` constants in `gateway-core/src/config.rs`; the limits a config may set (16 upstreams per route, 256 aliases, ...) are `MAX_*` constants beside their types, and `examples/wye.toml` states those an operator sets (validation errors name the rest, such as the format of an upstream id).

## Invariants

1. No full-response buffering for streaming.
2. Bounded memory under a slow downstream consumer.
3. Client cancellation releases gateway resources and attempts upstream cancellation.
4. Tool-call and event streams preserve ordering and identifiers for supported pairs.
5. Every failover follows an explicit safety and deadline policy.
6. A configuration snapshot is consistent within a request.
7. Authentication and model permissions are checked before upstream work; output-token ceilings and the size limit are also checked as the body streams, and a violation aborts the upstream request before the provider has the whole body.
8. No request depends on cross-request quota or history.
9. Only allowlisted request fields are rewritten; a caller's limit is never raised.
10. Usage observation never alters, delays, or buffers forwarded bytes.
11. Requests referencing upstream-held state reach the upstream that holds it, or are refused.
12. Choosing the route and the upstream is a pure function of request, token, and config, so `wye explain` and replicas always agree.

## Open design decisions

Each topic with the current preference or the unresolved point:

- **`include_usage` injection**: per-route; default undecided until client compatibility is tested.
- **Configuration reload**: startup snapshot first; hot reload only on demand and without disrupting streams.
- **SigV4 for AWS providers**: sign per request (an HMAC chain, microseconds) with an unsigned payload hash if Bedrock and Claude Platform on AWS accept it (to verify), since hashing a streamed body first would mean buffering it; otherwise support only their API keys.
- **Vertex access tokens**: token exchange inside Wye (service-account key, RS256 JWT, one call per hour, in-memory cache) or an external refresher writing a token file; undecided.
- **Edge support**: WASM adapter after native correctness.
- **Package registries**: `wye` is taken on crates.io (as is `gateway-core`), so publishing there needs other names; releases ship as GitHub archives meanwhile.
