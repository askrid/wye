# Product

Wye is a gateway between AI agents or AI-native apps and the model providers. Clients keep the provider's official SDK and native API, and get every new provider feature on the endpoints Wye serves the day it ships. Which model and provider serve a request, provider keys, limits, failover, upgrades, telemetry, and cost move out of their code into one reviewed config in Git. Wye does this per request and statelessly, as one binary with one TOML file and no database.

The [README](../README.md#what-it-does) says what it does, who it is for, and why native APIs pass through. [roadmap.md](roadmap.md) has the status and the order of the next work. Spend was part of the motivating case. A team stopped using an AI gateway once its model spend became hard to justify or control, so Wye bounds spend without a ledger of its own ([what it can enforce](policy.md#state-boundary)).

## Principles

Every feature follows these, and a feature that cannot is not built.

- **Native and transparent.** Each client's native API passes through to its own provider, and bodies are forwarded unchanged beyond the [allowlist](architecture.md#forwarding-contract). New provider features work through Wye without a Wye release. Usage records carry ids, counts, and keyed hashes, never prompt text. An endpoint counts as supported only once its request fields, tool-call identifiers and argument fragments, event ordering, finish reasons, errors, usage, and cancellation are tested.
- **Report, don't rewrite.** Where a client's request will break (an upgrade, a policy), Wye refuses explicitly or reports it. It never silently changes what the client asked for. The one field it changes, the model, changes only where reviewed config says so (an alias, a provider's own model id such as Bedrock's, or, planned, a [size-aware model routing](glossary.md#planned) rule the operator turns on), and never out of sight, since the response names the model that ran and the usage record keeps both.
- **Request-local and stateless.** A decision uses only the request, its [gateway token](glossary.md#access), and the immutable config; correlation across requests happens in the user's [OpenTelemetry backend](glossary.md#usage-and-cost), whichever vendor runs it. Nothing moves between replicas ([policy.md](policy.md#state-boundary)).
- **Fast and light.** The request path reads headers, and the body only where a policy or a scan needs it; keying, encoding, and aggregation happen in the usage writer task. A streamed event allocates nothing, and every queue and metric series has a fixed bound. Body scans are opt-in and sampled unless they are cheap enough to run on every request.
- **Little to set up.** Working defaults, so a local gateway needs a few config lines; `base_url` plus a token for any SDK; one command per agent (`wye claude`, `wye codex`); errors that say what to change; prebuilt binaries and images; no required cloud platform. A feature that needs a manual to set up is not done.
- **One responsibility.** Inference traffic only, with no agent loop, tool execution, MCP proxying, dashboard, or stored usage history.

## Positioning

The landscape as of 2026-10, agentgateway rechecked 2026-11-13. Competitor features change quickly; re-check them before publishing any comparison.

- **No gateway**: SDK calls straight to the provider, API keys per service, the provider console's workspaces, spend limits, and usage reports; agents' own telemetry. Wye moves provider keys, models, limits, and failover out of application code, and adds one telemetry and cost model across clients and upgrade checks. For a few services on one provider, no gateway is enough.
- **Claude apps gateway**: Anthropic's self-hosted Claude Code gateway, with SSO sign-in, model access by IdP group, and OTLP. Wye differs in service and CI tokens, SDK apps and other agents, aliases, multi-provider Claude, and policy tests. A team that uses only Claude Code and has SSO should prefer it, since it tracks every Claude Code release by construction.
- **LiteLLM**: the common open-source gateway, with a unified API across many providers, virtual keys, budgets, fallbacks, and an admin UI; it needs a database for spend. Wye needs no database and passes native APIs through, so it has no feature lag; it uses less CPU per streamed event in the same benchmark ([benchmarks.md](benchmarks.md#results)) and has far fewer providers by design.
- **Newer lean gateways** (agentgateway, Bifrost, Portkey, Helicone's gateway, and others): fast open-source gateways, several with dashboards, budgets, and many providers. agentgateway 1.7 (2026-10-27) also records Claude Code's session and summarizes its request log (`agctl standalone analytics`). Wye adds subagent, request-class, and tool-time attribution without extra config, a cause for each prompt-cache miss, stateless GitOps policy, and upgrade checks. They compete on speed too; in each comparison on the same machine, Wye used less CPU per request ([performance](../README.md#performance)).
- **Hosted gateways** (Cloudflare, Vercel, Kong, OpenRouter): managed, nothing to run. Wye is self-hosted, so the customer controls the path and the data.
- **Observability tools** (Langfuse, Arize, provider analytics): traces and analytics of LLM calls, through SDKs or exports. Wye captures usage at the gateway from verified gateway tokens, so a client cannot switch it off, and without instrumentation; it is no replacement for evaluation tooling.
- **Local usage tools** (surveyed 2026-10-30): Claude Code's own [`/usage`](https://code.claude.com/docs/en/costs), [status line](https://code.claude.com/docs/en/statusline), and opt-in [OTel events](https://code.claude.com/docs/en/monitoring-usage) show one session's cost, main-thread cache misses with their likely cause, and plan limits, with no history without a backend. [ccusage](https://github.com/ryoppippi/ccusage) reports history from transcripts, which in one checked log missed 59 auxiliary requests, a compaction, and a 429 (about 7.5% of API-equivalent spend), with no timing or tools. [better-ccflare](https://github.com/tombii/better-ccflare) and [Bifrost](https://docs.getbifrost.ai/cli-agents/claude-code) keep per-request bodies in SQLite. Wye records every request, auxiliary ones included, with subagent, tool, and cache-miss structure, and needs no database; the planned [waste report](roadmap.md#m2c-fewer-expensive-tokens) is meant to make it worth installing on its own.

### Lasting differences

Speed, statelessness, and single-binary distribution are necessary, and others can copy them. Two records build up over time and need ongoing upkeep. One is an understanding of agent traffic, turned into attribution and explanations; the other is each model's breaking changes, turned into upgrade checks so teams upgrade models by config with evidence. Correctness proven per client release (Claude Code's gateway contract changes per release) and policy as code without a database add to that.

Provider gateways can add the same analytics for their own clients, and lean gateways can add agent awareness. Neither serves several clients and providers behind one native-passthrough policy and one telemetry and cost model, with CI and service identities and the data in the team's own [OpenTelemetry backend](glossary.md#usage-and-cost).
