# Operations

Distribution, CLI, deployment, telemetry, and failure behavior. The gateway binary is an ordinary inference server: IaC, DNS, certificates, infrastructure secrets, scheduling, and autoscaling are not implemented inside it.

## Distribution

Release archives and a local OCI image are built; the rest of this list is planned.

- Versioned Linux and macOS binaries (implemented). A `v*` tag runs `.github/workflows/release.yml`, generated by [dist](https://github.com/axodotdev/cargo-dist) from `dist-workspace.toml`. It builds x86_64 and arm64 Linux (glibc 2.35 or newer) and macOS, each on a native runner with the benchmarked `release` profile, and publishes a GitHub Release with `.tar.xz` archives, SHA-256 checksums, build provenance attestations (`gh attestation verify`), and a shell installer. No Windows build. Edit `dist-workspace.toml` and run `dist generate`, never `release.yml` by hand.
- A signed, versioned OCI image (built locally only; publishing and signing are not set up). The `Dockerfile` builds a release binary into distroless `cc` (glibc, no shell, non-root), with a `HEALTHCHECK` that runs `wye probe` against `/readyz`. Inside a container Wye listens on `0.0.0.0`, which requires `[auth]`. `scripts/image-smoke.sh` checks that the image becomes healthy, answers `/readyz`, and rejects an unauthenticated request.
- Docker Compose example for a VM.
- Helm chart for Kubernetes.
- Terraform reference examples where useful.
- Later: Cloudflare Workers / Fastly Compute Rust/WASM adapter, subject to streaming and API constraints.

## CLI

`wye --help` lists the commands and `wye <command> --help` a command's options. Both are generated from the table the parser reads, so help cannot drift. Options follow the GNU conventions: any order, `--name value` or `--name=value`, `-c` for `--config`, and `--` before arguments that start with a dash.

**Exit status**: 0, or 1 with an error on stderr; 3 when `doctor` finds a problem, `explain` a refusal, `policy-test` a failed case, `policy-diff` widened access, or `service status` a service that does not answer.

**Output.** Help and `wye report` fit 80 columns; `explain` prints one long line per step, for `grep`. Data goes to stdout and messages to stderr, and a reader going away (`wye report | head`) ends a command quietly. On a terminal, color marks only what carries meaning: bold headings, cyan for a command to copy, and green or red for verdicts and errors. It is off when the output is not a terminal, `NO_COLOR` is set, or `TERM=dumb`.

### Files

A user's files live in `~/.wye`, or `$WYE_HOME`:

| File | What it is | Written by | Read by |
|---|---|---|---|
| `wye.toml` | The config | `wye init` | every command that takes `-c` |
| `usage.jsonl` | Usage records | `wye service`, or your redirect | `wye report` |
| `wye.log` | The background gateway's messages | `wye service` | you, when it does not answer |
| `issuer.key` | The signing key, mode 600 | `wye init --team`, `wye token keygen` | `wye token issue`; never the gateway |
| `anthropic.key`, `openai.key` | Provider keys, next to a config that names them | you | the gateway |

A command that reads a config takes `-c <path>`, else `$WYE_CONFIG`, else `~/.wye/wye.toml`. A `wye.toml` in the working directory is read only when named (`-c wye.toml`, or `export WYE_CONFIG=$PWD/wye.toml` in a config repository): a config decides where your credentials go, so the one in a repository you just cloned must not apply by itself. `serve`, `doctor`, `explain`, `policy-test`, and `validate` print the config they read, and errors name it.

### Environment variables

Read by `wye`:

| Variable | Meaning | Used by |
|---|---|---|
| `WYE_CONFIG` | The config, when `-c` is not given; the container image sets `/etc/wye/wye.toml` | every command that takes `-c` |
| `WYE_HOME` | Your files (default `~/.wye`) | every command |
| `WYE_URL` | The gateway (default `http://127.0.0.1:8080`) | `claude`, `codex`, `probe` |
| `WYE_TOKEN` | The gateway token; removed from the agent's environment. Set but empty is an error, rather than falling back to the agent's own login | `claude`, `codex` |
| `WYE_CLAUDE_BIN`, `WYE_CODEX_BIN` | Another path to the agent | `claude`, `codex` |
| `NO_COLOR`, `TERM` | No color when `NO_COLOR` is set or `TERM=dumb` | every command |

Set but empty counts as unset, except `WYE_TOKEN`.

Named by the config, read once at startup; the names are yours to choose, and these are the usual ones:

| Field | Usual variable | Holds |
|---|---|---|
| `api_key_env` | `ANTHROPIC_API_KEY`, `OPENAI_API_KEY` | A provider key |
| `cache_diagnostics.hash_key_env` | `WYE_CACHE_HASH_KEY` | The key for prompt-section hashes |
| `telemetry.otlp_headers_env` | | Headers for OTLP export |

Set for the agent by `wye claude` and `wye codex`:

| Variable | Set to |
|---|---|
| `ANTHROPIC_BASE_URL` | The gateway |
| `ANTHROPIC_AUTH_TOKEN` | The gateway token, if there is one; `ANTHROPIC_API_KEY` is then removed, since Claude Code would prefer it |
| `CLAUDE_CODE_GATEWAY_HINT_HEADERS` | `1`, unless you set it |
| `WYE_CODEX_TOKEN` | The token Codex sends |

Clients read their own: the SDKs' `ANTHROPIC_BASE_URL`, `ANTHROPIC_API_KEY`, `OPENAI_BASE_URL`, and `OPENAI_API_KEY` ([using it from apps](guide.md#using-it-from-apps)), and Claude Code's `CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY` and `CLAUDE_CODE_API_KEY_HELPER_TTL_MS`. Variables for the benchmark and scripts are in [development.md](development.md#scripts-and-benchmark-variables).

### Commands

What `--help` does not say.

**`wye init`**: [choosing a setup](guide.md#choosing-a-setup).

**`wye doctor`** checks what `serve` will need and says what to change, one line per check. Secrets go through the same functions `serve` resolves them with, so a check fails exactly when startup would. Every check runs, so one pass lists every problem.

- Each upstream's provider key is present, not blank, and valid in an HTTP header (never printed), and how it will be sent.
- A Bedrock upstream's base URL ends in `/anthropic`, where its Messages endpoint is.
- Each upstream answers at its base URL: one unauthenticated `HEAD`, trusting its `ca_file`, proves DNS, TCP, TLS, and HTTP, and nothing is billed.
- The identity providers' key sets, the cache-diagnostics hash key's length, and the OTLP header variable and endpoint. Headers sent over plain http beyond this machine are a problem, since they usually carry a backend's API key.

Not checked yet: model availability per upstream.

**`wye explain`** prints each check `serve` would make for one request, offline, calling the same functions in the same order: endpoint, token (verified at the current time), body size, alias, model permission, output-token ceiling, route upstream and failover order, upstream URL and provider key (by name, never value), the provider's model id, the price, whether cache diagnostics would hash it, and, with `--target-model` or `[upgrade_check]`, what each target would reject, the fix, and the source.

A refusal prints the status and error the server would send. The body is read as the server reads it: up to its `model`, then the rest when permissions or a ceiling apply. Not evaluated: run-time conditions (the concurrency limit, the held-bytes budget, upstream failures) and request headers (the server answers a compressed or non-UTF-8 body under a policy with `415`).

**`wye policy-test [<dir>]`**: `<name>.expect.toml` states the decision for the request body `<name>.json`: `decision = "forward"` or `"refuse"`, optionally `status`, `error`, `model` (the model the request runs on, after aliases), `upstream`, `path`, `session`, and a `[token]` table (`subject`, `models`, `max_output_tokens`). Tokens would expire in CI, so a case states the token's claims and only the signature check is skipped. [`examples/policy-tests/`](../examples/policy-tests) has a config and four cases, and the test suite runs them.

**`wye policy-diff <old> <new>`** prints what a config change widens, narrows, or only changes, and exits 3 when anything widens, so CI can ask for a second review. Key sets are read relative to each config, so compare against a checkout of the base: `git worktree add ../base main && wye policy-diff ../base/wye.toml wye.toml`.

- Widening: authentication removed, a listener moved beyond loopback or onto every interface, a model newly allowed by `[auth] models` or an identity provider's grant, a raised or removed `max_output_tokens`, a longer `max_token_ttl_secs`, a newly trusted signer (a signing key, Wye's own tokens, an identity provider, a key in its key set, or a changed audience, algorithm, or subject claim), a route for an API that had none, and an upstream that starts sending the operator's key where callers brought their own.
- Model patterns compare by coverage, so `claude-*` → `claude-opus-*` narrows.
- Listed for review only: upstreams added, removed, or moved within a route, and a changed key source. Where requests go is not who may send them.
- Not compared: aliases (permissions apply to the model an alias resolves to) and tokens (a token can only narrow what config allows).

**`wye report`**: [reading it](guide.md#reading-wye-report).

**`wye probe [<url>]`** sends one `GET` and exits 0 only for a 2xx answer within 5 s. A URL without a path names a gateway and asks its `/healthz` (the gateway's `/` serves nothing). A path is asked as given, such as `/readyz` for a load balancer's view.

**`wye token issue <subject>`** signs a gateway token offline ([policy.md](policy.md#gateway-tokens)) and never runs inside the server. The key id comes from the `[[auth.keys]]` entry whose public half matches the key, so a rotated key needs no flag. A `--ttl` above `max_token_ttl_secs` is refused, as the server would refuse the token. A service that mints tokens does the same with a config of its own.

### Client wrapper

**`wye claude`** checks that the gateway answers `/healthz`, sets the [variables above](#environment-variables), and replaces itself with `claude` (Unix `exec`). Signals, the terminal, and the exit code are Claude Code's own, and nothing is written. Without a token, Claude Code keeps its own login or API key.

- `claude` is found on `PATH`; a shell alias is not applied.
- Arguments after `--`, or from the first one wye does not know, go to Claude Code unchanged (`wye claude --resume <id>`; `wye claude -- --help` for its own help).
- A gateway beyond this machine must be `https`: plain http would carry the token, or Claude Code's own login, in the clear.
- Claude Code sends hint headers (request class, prompt id, tool times) to a custom base URL only when asked, hence `CLAUDE_CODE_GATEWAY_HINT_HEADERS`.
- The URL and the hint setting also go to Claude Code as `--settings`, because background sessions (`wye claude --bg "task"`) are started by its daemon, which does not inherit the wrapper's environment. The token never goes that way, since other local users can read a command line; a background session behind `[auth]` gets its token from [`apiKeyHelper`](#token-renewal).
- `CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY=1` makes Claude Code's `/model` picker read `GET /v1/models` when the config has `[discovery]`.

The steps per setup are in the [guide](guide.md#running-it).

**`wye codex`** takes the same options and environment. It runs `codex` with command-line config overrides that define a provider `wye` (`base_url` = the gateway plus `/v1`, `wire_api = "responses"`, `env_key = "WYE_CODEX_TOKEN"`) and select it. Without a gateway token, `WYE_CODEX_TOKEN` is a placeholder, which a gateway without `[auth]` replaces with its OpenAI key. `~/.codex/config.toml` is not touched; arguments after wye's own go to Codex (`wye codex exec "fix the tests"`). The gateway needs `[routes.openai]`; with `[auth]`, use a token without an output-token ceiling, since Codex does not set `max_output_tokens` ([policy.md](policy.md#per-request-ceilings)). What Codex sends: [architecture.md](architecture.md#codex-integration).

### Token renewal

Short-lived tokens need a command that fetches a fresh one, so nobody pastes tokens. Claude Code's [`apiKeyHelper`](https://code.claude.com/docs/en/llm-gateway-connect) setting runs a shell command that prints the token and sends its output as both `Authorization: Bearer` and `x-api-key`. It caches the token for five minutes (`CLAUDE_CODE_API_KEY_HELPER_TTL_MS` changes that).

`ANTHROPIC_AUTH_TOKEN` and `ANTHROPIC_API_KEY` take precedence over the helper, so leave both unset (and run `wye claude` without `--token-file` or `WYE_TOKEN`). The helper can be distributed through managed settings. Each new token costs one full verification per connection, then the [per-connection cache](policy.md#gateway-tokens) applies.

In GitHub Actions, the job's OIDC token is the gateway token, so the repository holds no secret. Wye trusts the issuer ([`[[auth.issuers]]`](policy.md#gateway-tokens)):

```toml
[[auth.issuers]]
issuer = "https://token.actions.githubusercontent.com"
audience = "wye-prod"
algorithm = "RS256"
jwks_file = "github.jwks"          # https://token.actions.githubusercontent.com/.well-known/jwks
subject_claim = "repository"       # usage per repository
[[auth.issuers.grants]]
claim = "repository_owner"
value = "acme"
models = ["claude-sonnet-*", "claude-haiku-*"]
```

The job asks GitHub for a token with Wye's audience on every helper run:

```sh
#!/bin/sh
# scripts/wye-token.sh: prints a fresh GitHub Actions OIDC token for Wye.
curl -fsS -H "Authorization: bearer $ACTIONS_ID_TOKEN_REQUEST_TOKEN" \
  "$ACTIONS_ID_TOKEN_REQUEST_URL&audience=wye-prod" | jq -r .value
```

```yaml
permissions:
  id-token: write                  # lets the job request OIDC tokens
  contents: read
steps:
  - uses: actions/checkout@v7
  - run: |
      mkdir -p .claude
      echo '{"apiKeyHelper": "sh scripts/wye-token.sh"}' > .claude/settings.local.json
      claude -p "fix the failing tests"
    env:
      ANTHROPIC_BASE_URL: https://wye.internal.example.com
      CLAUDE_CODE_API_KEY_HELPER_TTL_MS: "240000"   # refresh within the token's lifetime
```

GitHub does not document the token lifetime (its example token is valid for five minutes), so keep the helper's cache lifetime below it; Wye rejects an expired token with `401`, and `max_token_ttl_secs` bounds what it accepts.

Developers use the same setting with a helper that prints a token from an issuer Wye trusts: the team's IdP (an `[[auth.issuers]]` entry), or an internal service that authenticates the developer by SSO and mints a short-lived gateway token with `wye token issue` (the signing key stays in that service). Offboarding then happens at the IdP: the next renewal fails, and the last token expires on its own ([revocation](policy.md#revocation)).

## Deployment modes

| User | Topology | Integration |
|---|---|---|
| Solo developer | Native binary, as a user service | `wye service install`, then `wye claude` |
| Small team | Internal container or VM behind HTTPS | SDK base URL + gateway token |
| Web backend on multi-region Kubernetes | Deployment + ClusterIP Service per cluster/region | Backend → cluster-local Wye DNS |
| Public AI app | Backend sidecar or shared internal Service | App owns user quotas; Wye routes inference |
| Serverless (e.g. Vercel) | Separate gateway service; a serverless adapter is future work | Backend → Wye |
| Edge | Future WASM adapter | Platform-managed transport and scaling |

Wye itself speaks plain HTTP, so a gateway beyond one machine goes behind something that terminates TLS: a platform's load balancer, an ingress, or a proxy on the same host. `wye claude` and `wye codex` refuse a remote gateway over plain http, since it would carry the token in the clear. With [Caddy](https://caddyserver.com/docs/quick-starts/reverse-proxy), which gets a certificate on its own and flushes event streams as they arrive (not yet run against Wye):

```text
wye.example.com {
    reverse_proxy 127.0.0.1:8080
}
```

For a public app, a shared internal Deployment is preferred when many app replicas share a gateway; a sidecar per Pod gives stronger locality and independence.

On Kubernetes, a Helm release (planned) would declare a Deployment, ConfigMap, Secret references, Service, readiness and liveness probes, shutdown grace, resources, and optional OTel environment. Wye has no Kubernetes client and no peer discovery. A CPU-only HPA can mislead for I/O-bound SSE; an external metrics adapter can use active streams and memory.

Nginx and app servers in front of SSE must disable proxy buffering and use a server model suited to long-lived streams (e.g. ASGI rather than blocking WSGI workers).

### Running as a service

On one machine, `wye service install` keeps the gateway running across logins and restarts it if it stops, through the operating system's own service manager, as you. It needs no sudo and changes nothing outside your home directory.

It writes a LaunchAgent (`~/Library/LaunchAgents/dev.wye.gateway.plist`) on macOS or a systemd user unit (`~/.config/systemd/user/wye.service`) on Linux, which runs `wye serve --config <config>` with stdout appended to `usage.jsonl` and stderr to `wye.log`. `--dry-run` prints the plan and the file and changes nothing. Before it changes anything it shows what it will do and asks; `--yes` skips the question (required without a terminal).

Before installing, the config is checked as the service will start it: it parses, every file it names is readable, and no secret comes from an environment variable, since a service does not inherit your shell's environment.

- Provider keys go in files next to the config (`api_key_file = "anthropic.key"`, readable only by you), which is how `wye init` writes them.
- The cache-diagnostics hash key and OTLP headers come only from the environment, so a config that uses them needs a service definition of your own. Start from what `--dry-run` prints for a config without them.
- If another gateway already answers on the config's port, such as `wye serve` in a terminal, the install stops.
- Under systemd, it refuses paths containing spaces, quotes, `$`, or a backslash.

```bash
wye service status      # installed? what it runs, the log's size, whether it answers
wye service restart     # after editing the config or installing a new wye; checks the config first
wye service uninstall   # stops it and removes the file; the config and the log stay
```

Replacing a running service waits for its gateway to finish its requests, up to the stop timeout: the config's drain delay and shutdown grace plus 5 s (35 s by default). New connections are refused until then. A restart ends open streams after that grace; Claude Code retries them. `restart` refuses a config that would not start and leaves the running service as it was.

On Linux, a user service stops when you log out unless lingering is on (`loginctl enable-linger`). The log grows without limit: rotate it, or truncate it after `wye report`.

### Without Kubernetes

Because Wye keeps no state, every multi-node setup has the same shape: a load balancer in front of identical processes reading the same config. For example:

| Platform | Shape |
|---|---|
| EC2 Auto Scaling group + ALB | Instances fetch the binary and `wye.toml` (S3) and the provider key (SSM) at boot; instance refresh rolls deploys |
| ECS / Fargate | One service with N tasks; the load balancer health check targets `/readyz` |
| Docker Swarm | `docker service create --replicas N`, configs and secrets built in, `--update-order start-first` |
| Nomad | One job with `count = N`, Consul health checks |
| VMs + HAProxy or Caddy | systemd units; config from Ansible or Git |
| Fly.io-style regional hosting | The native binary in several regions behind anycast: the practical form of "edge" today |

For rolling updates without dropped streams, give the platform a stop timeout above `drain_delay_secs + shutdown_grace_secs`. Load balancers in front must not buffer SSE, and their idle timeout must exceed silent gaps in a stream (around 300 s; the AWS ALB default of 60 s is too short).

For container platforms, `upstream.api_key_file` reads the provider key from a mounted secret file at startup, and [`wye probe`](#commands) is the health check for images without `curl`.

### Sizing (estimate)

From the TLS-path benchmark on a laptop, not yet measured on EC2: a heavy Claude Code user (about 5 concurrent streams, 250 events/s, 150 KB/s of resent context) costs Wye about 10 ms of CPU per second, about 1% of a core, and under 100 KB of memory. A 2-vCPU instance would serve roughly 130 heavy or 400 typical users at 70% CPU. Provider rate limits bind first; run two small instances for availability rather than capacity. Confirm with `wye-bench` on the target instance type and a separate load machine.

Wye does not lower a stream's tokens per second. It adds a roughly constant delay per event that does not accumulate: about 0.2 ms p50 at light load and 1.4 ms with 2,000 streams on the laptop, against the provider's 10-20 ms between tokens. Model permissions and cache diagnostics add cost per request and per uploaded MB, not per streamed event.

One Tokio worker held about 1,500 paced streams (36,000 events/s) within 10 ms of added p99. Latency, not CPU, sets the limit, so size by streams per core ([measurements](benchmarks.md#current-harness-and-baseline)). Multi-core figures need a separate load machine.

### Several Anthropic accounts

A team whose usage outgrows one account's rate limits, or that splits spend across accounts, lists them under `[routes.claude]` instead of `[upstream]` ([example](../examples/wye.toml)). `[routes.openai]` works the same way.

- Each session stays on one account, chosen from its session id (SDK callers without one: from the token subject), so prompt caches keep hitting ([cache-affine routing](architecture.md#cache-affine-routing)).
- Weights share sessions, not tokens. Adding an account moves only the sessions it now wins; removing one moves only its own, and their next turn writes the cache again at the new account.
- With `failover = ["429", "529", "connect"]`, a refused request goes to the session's next account within the same turn ([failover](architecture.md#claude-across-providers-m4)). Without it, a `429` goes back to the client, whose retry reaches the same account.
- `select = "ordered"` makes the first account primary and the others standby.
- `wye explain --session <id>` shows which account a session uses; records, OTLP, and `wye report` split usage and cost by `upstream`.

## Telemetry

One usage record per proxied request, written as a JSON line to stdout and, with `[telemetry] otlp_endpoint`, exported as OTLP over HTTP with JSON encoding: a log record and a span per request, plus cumulative metrics. No Prometheus endpoint; a collector is optional. Records never contain prompts, completions, or credentials. Telemetry is not a quota ledger: records can be lost and counters reset ([policy.md](policy.md#state-boundary)).

The usage record:

| Field | Values | Notes |
|---|---|---|
| `event`, `unix_ms`, `path`, `status` | `request`, time, route, HTTP status | |
| `outcome` | `completed` \| `failed` \| `cancelled` \| `gateway_error` | Recorded when the response body is dropped, so every outcome is counted; a client that leaves before the response headers is `cancelled` with `status` `499` |
| `duration_ms`, `headers_ms` | milliseconds | `headers_ms` = time to response headers |
| `upstream` | the route upstream's `id` | With `[routes.claude]` or `[routes.openai]`; absent with `[upstream]` and for requests refused before routing |
| `failovers` | `[{"upstream": "a", "status": 429}]`, or `"error": "connect"` | Attempts refused before the one that answered, in order ([failover](architecture.md#claude-across-providers-m4)); absent when none |
| `subject` | token subject | With `[auth]` |
| `session_id` | the client's session (Claude Code's or Codex's) | Kept only as a bounded token (below) |
| `requested_model` | the [alias](architecture.md#model-aliases-and-upgrade-checks) the client named | Only when an alias was resolved |
| `model`, `usage_status` | reported model; `complete` \| `partial` \| `unknown` \| `not_observed` | Streaming and non-streaming (JSON) responses are read; `not_observed`: errors, `count_tokens`, other content types |
| `upgrade_issues` | target model → rules it would reject | Checked requests only ([upgrade checks](architecture.md#model-aliases-and-upgrade-checks)); `{}` when none |
| `cost_usd`, `cost_status`, `pricing_version` | exact decimal string; `complete` \| `partial` \| `unknown`; `pricing.version` | With [`[pricing]`](policy.md#pricing-metadata); `cost_usd` only when a cost was computed |
| `input_tokens`, `output_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens` | counts | As the provider reports them, except that on the OpenAI APIs the cached share of `input_tokens` (Chat: `prompt_tokens`) is moved to `cache_read_input_tokens`, so `input_tokens` excludes cache reads on every API |
| `request_class` | `main` \| `subagent` \| `workflow` \| `compaction` \| `auxiliary` \| `other` | Claude Code's hint header; for Codex, from `x-openai-subagent` ([mapping](architecture.md#codex-integration)) |
| `agent_type`, `agent_id`, `parent_agent_id`, `prompt_id` | tokens | Claude Code: `agent_id`s on every subagent request; the rest need `CLAUDE_CODE_GATEWAY_HINT_HEADERS=1`, which `wye claude` sets. Codex: thread ids as agent ids, the subagent kind as `agent_type`; no prompt id |
| `compaction`, `context_compacted` | `auto` \| `manual` \| `reactive` \| `other` | Hint headers |
| `tool_durations` | `[{"name": "Bash", "ms": 742}]` | Tool calls since the agent's previous request; at most 32 |
| `tool_calls` | `{"Bash": 2, "Read": 1}` | Tool calls the response started (`tool_use` blocks, Responses call items, Chat tool calls); at most 8 names, the rest under `(other)`; inputs never read |
| `cache_miss` | `compaction` \| `after_compaction` \| `unexplained` | A cache write with no cache read; the first cache write of a session or a subagent also reads `unexplained` |
| `prompt` | keyed prompt hashes | With [`[cache_diagnostics]`](research.md#2-cache-miss-diagnostics), sampled sessions only: `status`, `tools` and `system` (`count`, `hash`), `messages`, `breakpoint_count`, up to 4 `breakpoints`, the last 8 `message_prefixes`; 16-hex HMAC-SHA256 tags |

Client-supplied values are labels, never authorization: closed vocabularies map to fixed strings, and ids outside 1-128 bytes of letters, digits, `-`, `_`, `.`, `:` are dropped. Planned fields: `ttft_ms`, `config_version`. No `provider`: the upstream's `id` names the account, and config maps it to its provider.

OTLP logs: each record becomes a log record at `{otlp_endpoint}/v1/logs`, resource `service.name` (`telemetry.service_name`, default `wye`) and `service.version`. Attributes follow OpenTelemetry semantic conventions where they exist (`gen_ai.system`: `anthropic` or `openai` by endpoint, `gen_ai.response.model`, `gen_ai.usage.*_tokens`, `http.route`, `http.response.status_code`, `session.id`, `enduser.id`), then the agent fields of either client (`gen_ai.agent.id`, `gen_ai.agent.name` for the agent type, `wye.parent_agent_id`, `wye.request_class`, `wye.prompt_id`, `wye.compaction`, `wye.context_compacted`) and `wye.*` for the rest (`wye.outcome`, `wye.duration_ms`, `wye.headers_ms`, `wye.usage_status`, `wye.upstream`, `wye.requested_model`, `wye.cost_usd`, `wye.cost_status`, `wye.pricing_version`, `wye.cache_miss`; `wye.tool_calls`, `wye.failovers`, `wye.prompt`, and `wye.upgrade_issues` as JSON strings).

OTLP metrics are cumulative since process start, exported every 10 s and at shutdown; at most 256 attribute sets each; per process, summed by the backend.

| Metric | Kind | Attributes |
|---|---|---|
| `wye.requests` | sum | `http.route`, `wye.upstream`, `http.response.status_code`, `wye.outcome` |
| `wye.request.duration` | histogram, ms (5 ms to 300 s) | route, outcome |
| `wye.tokens` | sum | `gen_ai.token.type`, `gen_ai.response.model`, `wye.request_class`, `wye.upstream` |
| `wye.cost` | sum, USD | `gen_ai.response.model`, `wye.request_class`, `wye.upstream`; complete and partial costs, with `[pricing]` |
| `wye.upgrade.issues` | sum | `wye.upgrade.target`, `wye.upgrade.rule`, `enduser.id`; checked requests a target would reject |
| `wye.failovers` | sum | `wye.upstream` (the refusing one), `wye.failover.reason` (a status or `connect`) |
| `wye.tool.calls` | sum | `gen_ai.tool.name` |
| `wye.cache.misses` | sum | `wye.cache_miss` |
| `wye.requests.active` | gauge | |
| `wye.telemetry.lost` | sum | log records and spans lost to full queues, failed exports, or the series cap (a request losing both counts twice) |

`wye.upstream` is present only with a route's named upstreams (`[routes.claude]`, `[routes.openai]`).

OTLP traces have one server span per request (`POST` and the route, such as `POST /v1/messages`) with the record's attributes, a `response headers` event, and `ERROR` status for failures and 5xx. Parent: a valid `traceparent` header; else, with a client session id (Claude Code's or Codex's), the session's trace (trace id = first 16 bytes of SHA-256 of the prefixed session id, the same on every replica, so a whole session is one timeline); else a new trace. Each reported tool call becomes a sibling span `tool <name>` (`gen_ai.tool.name`, `wye.tool.duration_ms`) ending when the request starts (approximate: Claude Code's times exclude prompts and hooks). No synthetic prompt or subagent spans: no single request knows it is the first. The `traceparent` sent upstream is the caller's.

Bounds: records pass a 4,096-record queue to one writer task; OTLP batches go at 512 records or after 1 s through a queue of 8 batches, with a 10 s timeout per export. Anything dropped is counted and written to the usage log at shutdown (`usage_log_dropped`, `otlp_dropped`). A blocked usage log keeps OTLP running: up to one batch of records is kept for the log, and the rest are counted as dropped. `telemetry.otlp_headers_env` names an environment variable of extra export headers (`key=value,key2=value2`), treated as secrets; the export client trusts the upstreams' roots, every `ca_file` included.

## Health and shutdown

`/healthz` says the process is up, and is what `wye probe`, `wye claude`, and `wye service` ask. `/readyz` also fails while draining, so it is the one for load balancers and container health checks. Neither depends on a monitoring backend: a transient OTel outage does not block inference.

On SIGTERM, shutdown has two phases:

1. Draining (`server.drain_delay_secs`, default 0): `/readyz` returns 503 while `/healthz` stays 200, and new connections and requests are still served, so a load balancer removes the replica before connections are refused. Set it to cover the load balancer's probe interval and endpoint propagation (in Kubernetes, typically 5-15 s) instead of a `preStop` sleep.
2. Grace (`server.shutdown_grace_secs`, default 30): the listener closes, active requests may finish, and whatever remains is cancelled; cancelling a stream closes its upstream request.

Set the pod's `terminationGracePeriodSeconds` above the sum of both.

## Failure behavior

| Event | Behavior |
|---|---|
| Bad config or missing secret | Fail startup with an actionable diagnostic, without exposing secrets |
| Invalid or expired token | Reject locally |
| No eligible route | Explicit compatibility or policy error |
| Slow downstream | Bounded flow control ([upstream connections](architecture.md#upstream-connections)): streams sharing its upstream connection are unaffected, and a client that accepts no bytes for `client_write_timeout_secs` (60) is disconnected and its upstream request cancelled |
| Client body breaks (bad framing, cut off mid-upload) | `400`, recorded as a gateway error; the upstream request is aborted and not failed over |
| Client stops sending while its body is held | `408` after 60 s without bytes, or 5 minutes without reaching its `model`; its held bytes and permit are released |
| Request body breaks the policy or the size limit mid-upload | The upstream request is aborted before the provider sees the body whole; the client gets the refusal's own `400`, `403`, or `413`, from HTTP/1.1 and HTTP/2 upstreams alike |
| Upstream failure before downstream output | Gateway error; with `failover` on the route, the session's next upstream when the refusal proves the request was not processed ([retries and fallback](architecture.md#retries-and-fallback)) |
| Partial stream failure | Terminate the stream; never silently replay output. A successful Messages event stream that stalls past `stream_idle_timeout_secs` or breaks at an event boundary ends with an Anthropic `error` event (`overloaded_error`) and a clean close, so clients see a retryable API error; a Responses stream just ends, which Codex and the OpenAI SDKs retry; mid-event failures still drop the stream, since appending would corrupt the event |
| Client disconnect | Cancel upstream where possible, free resources, record uncertain cost |
| Telemetry export failure | Inference continues; loss visible in logs/counters |
| One replica dies | Others accept new connections; its streams fail |
| Fleet restart | Redeploy config and secrets; in-flight inference lost, no quota state to restore |
| Mixed config versions during rollout | Each request is decided by one replica's config; `config_version` in records is planned |
